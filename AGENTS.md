# AGENTS.md

Operating rules for AI agents working in this repository. Cursor loads this file
automatically for every request in this project.

## What this repository is

A **base template project for qlaris** — a clean starting point with the MCP server registered and
these operating rules already in place. There is no application source code, no build system, and no
test suite — what this repo produces is research artifacts (markdown briefs, HTML prototypes, viewer
pages) generated by qlaris-backed skills.

Everything runs through the qlaris MCP server: ad-hoc research via `with qlaris:`, and full pipeline
runs via the server-side discovery orchestrator. See `README.md` for setup and the command surface.

Do not look for `package.json`, lint configs, or CI. If a task seems to call for them, ask before
scaffolding.

## MCP configuration

`.cursor/mcp.json` registers a single HTTP MCP server:

```json
{ "mcpServers": { "qlaris": { "url": "https://app.qlaris.ai/api/mcp" } } }
```

`.cursor/permissions.json` allows every qlaris tool without a prompt:

```json
{ "mcpAllowlist": ["qlaris:*"] }
```

Entries are `server:tool` — the colon is required, and `server` is the key from `.cursor/mcp.json`.
Both files are checked in, so a fresh clone gets the server and its approvals. Toggling the server
on under Customize → MCPs is still a one-time per-machine step. See `README.md`.

qlaris is the research engine — it runs synthetic surveys, UX tests, and interviews against
digital-twin persona panels. **There is no fallback.** If the MCP is unavailable, stop and say so;
never substitute model roleplay for qlaris results.

## Mandatory routing triggers

These override normal judgment — they are enforced by the MCP server's own instructions:

| User phrase | Required first action |
|---|---|
| contains `with qlaris` (any casing) | call `help_with_qlaris` and follow the returned skill *before* responding |
| contains `qlaris knowledge` | call `query_knowledge`, render exactly as `## Summary` / `## Findings` / `## Sources` / `## Checks` |
| any other qlaris workflow question | `list_skills`, then `get_skill` on the match — do not improvise |

Never answer these from memory. `get_skill` must be called in the *current* conversation — a
remembered shape of a skill is not the skill.

## All skills live on the server, not in this repo

No skills live in this repo. All discovery skills are served by qlaris MCP. Discover with
`list_skills`, load with `get_skill`. Two families:

- **`discovery-*`** — the six-phase discovery pipeline plus `discovery-orchestrator` (runs it
  end-to-end) and `discovery-research-overview` (live dashboard / final report).
- **`business-model-evaluation-*`** — BMC, competitors, market sizing, moat, founder-fit, dashboard,
  plus an orchestrator for the full 7-phase evaluation.

## The discovery pipeline

Phases run in order; each is a distinct skill and each produces a compact handover for the next:

1. `discovery-opportunity` — frame and stress-test (Double Diamond + Cagan risks)
2. `discovery-solution` — explore the solution space (Double Diamond + OST)
3. `discovery-concept` — engineering-ready concept / PRD
4. `discovery-prototype` — `prototype.html` that *is* the real product with the new feature added
5. `discovery-validation` — broad panel research round **(never skip)**
6. `discovery-reconciliation` — concept + prototype re-validated in sync **(never skip)**

Then `discovery-research-overview` as a mandatory final step.

### Architectural rules the orchestrator enforces

- **One fresh agent context per phase.** The orchestrator starts a phase, waits, ingests the
  handover, verifies it, then starts the next. It never produces phase artifacts itself — this is
  deliberate, to remove the context pressure that causes rationalized passes. If the client cannot
  spawn a subagent, run each phase in a **new chat** and pass the handover forward; do not run the
  whole pipeline in one long conversation.
- **Handover verification gate.** A handover is rejected if it lacks a `## qlaris research sessions`
  table, lacks qlaris artifact URLs, or claims a pass without quantitative metrics. Session `N`
  values are re-checked against `get_survey_status` / `get_user_test_status`; any discrepancy =
  reject and re-run the phase.
- **Workspace first.** `list_workspace_contexts` → pick a workspace → that `workspaceId` is passed
  to every subsequent qlaris call and every `create_decision`.
- **Artifacts go through `serve_prototype`.** The qlaris URL is canonical; same slug re-uploads
  overwrite in place, so a bookmarked URL live-updates across a multi-hour run. Local files are a
  backup, not the source of truth.
- **Decisions are logged** via `create_decision` with `domain: "Pipeline"` — workspace choice,
  target outcome, run mode, panel designation, each gate verdict, each cross-phase jump, final
  go/no-go. Sub-skills log their own; do not re-log them.

### Quality gates — do not soften them

Thresholds are deliberately high (e.g. Likert mean ≥4.0/5 **and** ≥70% positive; single-choice
winner ≥60%; WTP ≥80% willing with 0% "would not pay"). Below threshold by any margin is a fail — no
rounding, no "practically equivalent", no "PASS with documented limitation".

The **lukewarm signal rule** overrides the numbers: polite agreement ("somewhat appealing",
"partially addresses") is not a pass even at a high percentage.

A **validation surprise** (≥40% on any signal that contradicts the upstream brief) means the
upstream framing was wrong — jump back and re-run downstream, do not file it as a minor note.

### Non-negotiables

- **No fabrication.** Ask for real inputs at intake; never invent context mid-flow. Predicted
  outcomes ("the panel would have failed") must never be written as observations — call the status
  tool and record what qlaris actually returned.
- **Panel designation is locked before research.** Which personas are gating vs. informing is
  recorded pre-run and cannot be revised after seeing results.
- **The pipeline is non-linear.** When a phase fails, root-cause first: if the cause is upstream,
  jump back rather than stalling.

## Working files and git

Two gitignored directories hold sensitive research data:

- `./context/` — inputs (`customer-intelligence.md`, `product-strategy.md`, `constraints.md`, …).
  Resolution order is qlaris workspace context **first**, local files as fallback.
- `./discovery/[slug]/` — per-run state (`orchestration-state.md`, `orchestration-defaults.md`,
  `orchestration-log.md`), phase handovers, briefs, `prototype.html`, `research-overview.html`,
  `concept.html`.

`orchestration-log.md` is append-only and designed to be watched with `tail -f` during long runs.

`.gitignore` already excludes `context/` and `discovery/`.

`.cursor/mcp.json` is tracked. The orchestrator's repo-setup step pulls from origin and merges
`.gitignore` entries but deliberately does not stage or commit — leave that to the user.
